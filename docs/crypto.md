# SafeMARC — Cryptographic & Package Security System

This document provides a detailed technical reference for SafeMARC's offline-first encryption and decryption architecture. It covers the underlying cryptographic primitives, key derivation functions, custom stream cipher, package structure for Identity Packages (`.smid`) and Custom Patterns (`.smpat`), and security mitigations against common archive exploits.

All cryptographic logic resides in `src/utils/crypto.py`, and is integrated into the import/export workflows in `src/gui/settings_dialog.py` and `src/gui/main_window.py`.

---

## 1. Core Cryptographic Architecture

SafeMARC operates as a strictly offline, local-only privacy utility. To protect sensitive reference photographs and proprietary text redaction patterns without requiring external database dependencies or cloud calls, SafeMARC uses standard python libraries (`hashlib` and `os`) to implement robust encryption.

### 1.1 Key Derivation — PBKDF2-HMAC-SHA256

User-supplied passwords are converted to high-entropy symmetric keys using the **PBKDF2 (Password-Based Key Derivation Function 2)** standard with SHA-256 as the underlying pseudorandom function:

- **Hash Function**: `SHA-256`
- **Salt Size**: `16 bytes` (cryptographically secure random bytes generated via `os.urandom(16)`)
- **Iteration Count**: `100,000` (designed to resist offline brute-force and GPU-accelerated dictionary attacks)
- **Derived Key Length**: `32 bytes` (256-bit symmetric key)

```python
key = hashlib.pbkdf2_hmac('sha256', password.encode('utf-8'), salt, 100000)
```

### 1.2 Symmetric Cipher — Custom SHA-256 Counter (CTR) Mode

Since the application runs in a lightweight, self-contained environment without binary third-party dependencies (like PyCryptodome), SafeMARC implements a **pure-Python Counter (CTR) mode stream cipher** powered by SHA-256.

- **Block Size**: 32 bytes (256 bits).
- **Keystream Generation**: For each 32-byte block `i` (0-indexed), the keystream is generated by hashing the concatenation of the 32-byte derived key and a 4-byte big-endian representation of the block counter:
  $$\text{Keystream Block } i = \text{SHA-256}(\text{Key} \parallel \text{Counter}_i)$$
- **Encryption/Decryption**: Symmetric XOR operation. Plaintext/ciphertext bytes are XORed bitwise with the keystream. Because XOR is self-inverse, decryption runs the exact same block loop.

```python
ciphertext = bytearray(len(data))
block_size = 32
num_blocks = (len(data) + block_size - 1) // block_size

for i in range(num_blocks):
    counter_bytes = i.to_bytes(4, 'big')
    keystream = hashlib.sha256(key + counter_bytes).digest()
    
    start = i * block_size
    end = min(start + block_size, len(data))
    for j in range(start, end):
        ciphertext[j] = data[j] ^ keystream[j - start]
```

### 1.3 Payload Output Format

The output of the encryption function is a single contiguous byte array structured as follows:

```
┌──────────────────────────┬────────────────────────────────────────────────────────┐
│  Salt (Bytes 0 - 15)     │  Ciphertext / Encrypted Payload (Bytes 16 onwards)     │
│  (16 bytes, random)      │  (Variable length, encrypted via SHA-256 CTR)          │
└──────────────────────────┴────────────────────────────────────────────────────────┘
```

During decryption, the first 16 bytes are sliced off to retrieve the salt, which is then fed into the PBKDF2 function alongside the password to derive the identical 256-bit key.

## 2. Identity Packages (`.smid`)

Identity Packages package local face recognition profiles (identities and their reference images) for backup or sharing across installations.

### 2.1 Export & Packaging Workflow

When a user exports one or more permanent identities via the Settings Dialog (`Ctrl+E`):

1. **Selection Filtering**: The system gathers selected permanent identities. Session-only identities are explicitly excluded.
2. **Directory Packaging**: A temporary, in-memory ZIP archive (`io.BytesIO`) is created.
3. **Artifact Exclusions**: For each identity, the system scans its directory and adds only the raw reference photographs (`.png`, `.jpg`, `.jpeg`, `.webp`, `.bmp`). Pre-computed biometric embeddings (`.sface.npy`) and grayscale LBPH cached crops (`.lbph.png`) are **excluded** to keep package sizes small and avoid potential platform-specific deserialization anomalies.
4. **Encryption**: The ZIP byte buffer is encrypted using the custom SHA-256 CTR cipher with a password-derived key.
5. **Output**: Saved to disk with the `.smid` extension.

```
Reference Photos
  ├── Alice/ref_0.jpg
  └── Bob/ref_0.png
         │
         ▼ (Zip compression, exclude cached .npy / .lbph.png)
   ZIP Payload (Bytes)
         │
         ▼ (XOR encrypt via password key + salt)
   .smid File on Disk (Salt + Ciphertext)
```

### 2.2 Import & Decryption Workflow

When importing an `.smid` package (`Ctrl+I`):

1. **Decryption**: The payload is decrypted using the derived key.
2. **ZIP Header Magic Verification**: The system verifies the decrypted bytes start with the ZIP local file header signature: `PK\x03\x04` (`0x50 0x4B 0x03 0x04`). If the signature is incorrect, it indicates a corrupted archive or an incorrect password, throwing an immediate validation exception.
3. **Zip Slip Security Mitigation**: SafeMARC defends against Zip Slip directory traversal vulnerabilities by validating every entry path in the archive. Any relative path containing `..` or leading absolute paths are rejected before extraction:
   ```python
   for member in zip_ref.namelist():
       normalized_path = os.path.normpath(member)
       if os.path.isabs(normalized_path) or normalized_path.startswith("..") or "/.." in normalized_path or "\\.." in normalized_path:
           raise ValueError(f"Malicious path detected in archive: {member}")
   ```
4. **Temporary Extraction**: The validated ZIP is extracted to a sandboxed directory in `tempfile.gettempdir()`.
5. **Identity Merging**: Valid identity subdirectories (containing supported images) are merged into the local permanent `identities/` folder.
6. **Retraining**: The system triggers a full refresh of SFace embeddings / LBPH training to integrate the imported identities immediately.

## 3. Custom Patterns (`.smpat`)

Custom Patterns allow users to export and import their customized text/regex matching lists.

### 3.1 Serialization & Format

1. **Data Model**: Custom patterns are stored as a JSON array of dictionaries containing:
   - `pattern`: The text or regex string.
   - `is_regex`: Boolean indicating if the pattern is a regular expression.
   - `whole_word`: Boolean indicating whether the match should align to word boundaries.
2. **Form Choice**: The user is offered two export choices:
   - **Password-Protected (`.smpat`)**: Encrypted via the custom stream cipher.
   - **Unencrypted JSON (`.json`)**: Raw plaintext JSON representation (no password required).

```json
[
    {
        "pattern": "\\b[0-9]{3}-[0-9]{2}-[0-9]{4}\\b",
        "is_regex": true,
        "whole_word": false
    },
    {
        "pattern": "CONFIDENTIAL",
        "is_regex": false,
        "whole_word": true
    }
]
```

### 3.2 Security Validation during Import

When importing `.smpat` or `.json` files:

1. **Decryption**: For `.smpat`, the file is decrypted.
2. **Format Verification**: The decrypted string is decoded as UTF-8 and parsed using `json.loads()`. If this raises a JSON/Unicode decode error, it triggers a warning (e.g. incorrect password).
3. **Schema Enforcement**: The parser validates that the root element is a JSON `list`. It iterates through each dictionary entry, ensuring necessary keys (`pattern`, `is_regex`, `whole_word`) exist with correct types, filtering out empty or invalid patterns.
4. **Regex Compilation Safety**: Before injecting imported regexes into `RegexDetector`, the patterns are passed through `re.compile()`. Malformed or dangerous patterns (such as those prone to catastrophic backtracking) are caught and reported, preventing application hangs.
5. **Immediate Rescan**: The patterns layout refreshes, and the scanner re-evaluates the active document with the new pattern set.

## 4. Cryptographic Diagnostics & Status

The `EngineStatusDialog` (accessible via Help or status bar click) displays whether the SFace ONNX model is available and initialized. If the SFace model is absent, the system notifies the user that the identity matching pipeline has downgraded to the classical LBPH fallback.

Additionally, the test suite includes `tests/test_import_export.py` which validates:
- Key derivation and encryption/decryption roundtrips.
- Error handling for invalid passwords.
- Zip Slip traversal defense mechanisms.
